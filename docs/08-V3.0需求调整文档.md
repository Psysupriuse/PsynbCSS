# 校园活动管理系统 V3.0 需求调整文档

> 依据：`docs/07-V3.0数据分析与问题发现.md`（对课程提供的 V2.0 模拟运行数据的分析）
> 基线：V2.0（三角色：学生/教师/系统管理员；报名状态机、候补递补、账号停用）
> 本轮工程意图：把"报名结果变化被动等学生回查"改为"系统内可见的状态变化提醒"，同时降低学生找活动的成本、明确报名提交结果反馈、适配以手机为主的访问形态。

## 1. 本轮调整的需求（共 4 项）

| 编号 | 需求 | 数据依据 | 优先级 |
|---|---|---|---|
| FR-V3-01 | 站内消息：报名/候补/审核结果变化时给学生发一条站内消息，导航栏显示未读数量，可一键全部已读 | 递补成功 130 个组合中 20% 无状态查看记录；28 条候补/状态不可见类反馈 | P0 |
| FR-V3-02 | 活动列表筛选与排序：按活动类型筛选、按开始时间筛选（本周/本月/周末）、按剩余名额排序 | 单会话打开详情 p50=3、p90=8；21 条查找类反馈（"想找周末的活动，试了几次才看到时间合适的"） | P0 |
| FR-V3-03 | 报名提交结果明确反馈：提交期间禁用按钮防重复点击，结果提示区分"报名成功/进入候补/待老师确认/人数已满/已结束/重复报名" | 126 次重复 apply（占 4.6%）；19 条结果不确定类反馈；SLOW_REQUEST 250 条 | P0 |
| FR-V3-04 | 移动端适配：学生端列表/详情/我的报名/消息页在手机宽度下可用 | mobile 访问占 70.9%，而 V2.0 规范明确不做移动端专项优化 | P1 |

## 2. 需求详情与验收标准

### FR-V3-01 站内消息（学生）

- 触发点：报名成功（含需审核活动的"待确认"）、进入候补、候补递补成功、审核通过/未通过。
- 消息内容：活动名称 + 结果描述 + 链接到活动详情。
- 学生端导航"消息"入口显示未读数（徽标）；消息页按时间倒序，支持"全部标为已读"。
- 验收：依次完成 报名→候补→递补→审核通过 四种场景，每种场景后未读数 +1，打开消息页后未读清零。

### FR-V3-02 活动列表筛选与排序（学生）

- 筛选维度：活动类型（下拉，来自 activities.category）、开始时间（全部 / 本周 / 本月 / 周末）、关键字（保留原有标题/地点搜索）。
- 排序：默认按开始时间；可选"剩余名额从多到少"。
- 筛选条件可组合；无条件时行为与 V2.0 一致。
- 卡片展示活动类型标签，减少"标题看着差不多"的问题。
- 验收：组合"类型=体育健康 + 周末"能只列出符合条件的活动；切换排序后顺序变化；清空条件恢复全量。

### FR-V3-03 报名结果明确反馈（学生）

- 报名/加入候补/取消/退出候补按钮：提交中禁用并显示"提交中…"，防止连点造成重复提交。
- 服务端返回的提示语按场景区分，失败必须说明原因（已结束 / 已满员 / 重复报名 / 活动不存在）。
- 验收：连点报名按钮只产生 1 条报名记录；满员时提示"已满员，可加入候补"；已结束时提示"活动已结束，无法报名"。

### FR-V3-04 移动端适配（学生端）

- 视口 < 768px：顶部导航改为可换行/紧凑布局；卡片单列；表格改为卡片式堆叠（我的报名、消息页）。
- 不影响桌面端现有布局。
- 验收：375px 宽度下学生端四个页面无横向滚动、按钮可点击、文字不重叠。

## 3. 明确不做（范围控制）

- 短信/邮件/微信通知：数据只证明"站内结果不可见"，没有证据表明需要外部通道；且需要外部凭据，超出本轮范围。
- 消息已读/未读的精细化（单条已读）：只做"全部已读"，避免过度设计。
- 活动推荐/个性化排序：数据不支持"推荐什么"，只做显式筛选与排序。
- 教师端、管理员端界面重构：本轮不动，仅保证不回归。

## 4. 对 V2.0 的影响

- `activities` 表新增 `category` 字段（教师发布/编辑活动时填写，默认"其他"）；V2.0 已有活动迁移为"其他"。
- 新增 `messages` 表（站内消息）。
- 报名/候补/审核/递补/取消的现有逻辑与状态机不变，只在对应成功分支追加写消息。
- 学生端新增"消息"导航项与消息页；列表页新增筛选表单。
