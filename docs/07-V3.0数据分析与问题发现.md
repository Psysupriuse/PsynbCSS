# 实验三 V3.0 数据分析与问题发现

> 数据来源：课程提供的《校园活动管理系统 V2.0 模拟运行数据》（`项目数据.zip`，解压后 `data/*.csv`，UTF-8 with BOM）。
> 覆盖时间：2026-09-21 至 2026-10-04（北京时间）。
> 说明：这是教师统一构造的教学样本，**不是本组 V2.0 系统自动导出的日志**；本报告只把它当作"观察性材料"用于发现问题，不用它冒充 V3.0 的实测结果。
> 分析脚本：`analysis/analyze.py`（纯 Python 标准库 csv，可复跑复核）。

## 1. 数据范围与粒度

| 文件 | 行数 | 粒度 | 本次用途 |
|---|---|---|---|
| registration_log.csv | 2878（apply 2748 / cancel 130） | 每次报名或取消请求 | 报名成功率、重复提交、耗时 |
| waitlist_log.csv | 1006 | 每次候补状态变化 | 候补规模与递补率 |
| user_behavior.csv | 11027 | 每次埋点事件 | 会话内浏览深度、设备分布 |
| feedback.csv | 112（26 种不同表述） | 每条匿名反馈 | 主观痛点 |
| system_log.csv | 792 | 每条系统日志 | 错误与慢请求 |
| activity.csv | 24 | 每个活动 | 容量、满员情况 |

数据限制（分析时已考虑）：埋点存在 28 条重复 `event_id`；`student_id`、`device` 存在少量空值；反馈文本是聚合后的短句，**不能当作全体用户的比例**；各表粒度不同，"访问次数 / 申请次数 / 人数 / 活动数"不可混算。

## 2. 关键统计结果

### 2.1 报名链路：候补是主流结果，重复提交显著

- apply 2748 次：accepted 1689（61.5%）、**waitlisted 876（31.9%）**、duplicate 126（4.6%）、capacity_conflict 41（1.5%）、server_error 16（0.6%）。
- 按活动看，17/24 个活动的报名人数达到容量上限；候补占比最高的活动 A005（候补 146/报名 200，73%）、A015（143/200，71%）、A021（141/194，72%）、A010（139/195，71%）。
- **126 组"同一学生对同一活动多次 apply"**，多出的 126 次请求全部是无效重复提交；其中客户端自报重试的也是 126 次，两者完全重合。
- 耗时：apply 整体 p50=256ms、p95=1573ms；其中 `waitlisted` p50=528ms、`capacity_conflict` p50=1308ms，明显高于 `accepted` 的 215ms。
- 系统日志 ERROR 57 条（E409 41 条对应 capacity_conflict，E500 16 条对应 server_error），WARN 中 SLOW_REQUEST 250 条、ASSET_RETRY 26 条。

### 2.2 候补结果不可见

- 递补整体发生率低：876 个进入候补的组合中只有 130 个发生递补（14.8%），原因码只有 `CAPACITY_FULL` 与 `SLOT_RELEASED`。
- **130 个被递补成功的组合中，26 个（20.0%）在埋点中没有 `status_view` 记录**——这些学生的报名结果变化完全没有被主动查看过。
- 反馈侧互相印证：8 条"我担心错过候补结果，经常自己去查状态"、7 条"之前以为还在候补，过了一阵再看已经是成功了"、5 条"有次候补转成功了，隔了两天打开页面才发现"、5 条"希望能更容易发现自己报名结果的变化"、4 条"报名状态发生变化时，我通常不会专门去页面查看"。

### 2.3 活动查找成本高

- 会话共 1416 个；**每个会话打开详情页 p50=3 次、p90=8 次、max=10 次**；到达报名页的 251 个会话此前平均打开 3.0 个详情。
- 反馈侧：10 条"活动标题看着差不多，打开详情才知道具体内容"、6 条"想找周末的活动，试了几次才看到时间合适的"、3 条"列表翻了几轮，来回点了不少详情页"、2 条"我只想参加一类活动，但需要自己逐个看"。
- V2.0 学生端列表只有"按标题/地点关键字搜索"一个入口，没有分类、时间筛选和排序，与上述现象一致。

### 2.4 移动端是主要访问设备

- 设备分布：mobile 7818（70.9%）、desktop 2848、tablet 339、空值 22。
- V2.0 的设计规范明确"以 1200px 宽为准，窄屏卡片换行即可，不做移动端专项优化"——70.9% 的访问发生在移动设备上，这是设计与实际使用形态的偏差。

### 2.5 报名结果反馈不清晰

- 反馈：7 条"报名失败了，但没有弄清楚原因，后来又试了一次"、7 条"页面卡住之后我又点了一次，提示内容有点难理解"、3 条"热门活动报名时转了一会儿，我不确定到底有没有提交成功"、2 条"我连续点了两次，想确认到底是否成功"。
- 结合 2.1 的 126 次重复提交与 p95=1573ms 的耗时，说明**提交后缺少明确、可理解的结果反馈**，用户用重复点击来确认。

## 3. 初步结论（进入需求调整）

数据指向四类问题，本组据此确定 V3.0 的调整范围：

| 编号 | 问题 | 主要证据 |
|---|---|---|
| P1 | 候补/报名结果变化学生不知道，只能自己反复回查 | 递补成功 20% 无状态查看记录 + 29 条相关反馈 |
| P2 | 活动列表筛选能力不足，找活动要逐个点开详情 | 会话详情打开 p50=3、p90=8 + 21 条查找类反馈 |
| P3 | 报名提交结果反馈不明确，引发重复提交 | 126 次重复 apply（4.6%）+ 19 条结果不确定类反馈 + 慢请求 250 条 |
| P4 | 主要访问设备是手机，但界面按桌面宽度设计 | mobile 占 70.9% |
